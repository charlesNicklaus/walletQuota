# 账户与金额区间报告设计

日期：2026-08-12

## 目标

在现有多渠道订单池综合报告中增加两类信息：固定金额区间统计，以及渠道可安全读取的收款账户/UPI 账户。ATG Pay 作为首个实现渠道，后续 Provider 可以使用同一账户模型返回本渠道数据。

## 已确认行为

- 金额分布改为连续且不重叠的区间：`<100`、`100-10000`、`10000-20000`、`20000-50000`、`>50000`。
- 区间边界使用左闭右开：`100 <= x < 10000`、`10000 <= x < 20000`；最后一个指定区间为 `20000 <= x <= 50000`。
- 每个区间输出订单数、金额小计，以及订单数占全部订单的百分比。
- ATG Pay 读取当前账号已绑定的收款 UPI 和银行卡。
- 如果当前账号已经领取订单，则读取这些订单的只读详情并列出对应收款方 UPI 或银行卡信息。
- 不自动领取新订单，不提交付款、不提交 UTR、不增删改 UPI 或银行卡。
- 终端中的账户标识脱敏；仅本地 `aggregate.json` 保存接口返回的完整账户标识。

## 已验证的 ATG 接口边界

所有接口均为 `POST`，沿用登录会话、`ts`、`userId` 和现有签名算法。

- `/user/upi/bind/list`：只读绑定 UPI 列表；请求 `accountType=1` 代表收款 UPI。返回 `bindUpiList`、`availableCount`、`unavailableCount` 和 `lock`。
- `/bank/debit/card/list`：只读银行卡列表，返回 `list` 和 `total`。
- `/pay/my/task`：只读当前账号已领取订单列表，分页返回 `list` 和 `total`。
- `/pay/order/detail`：只读一个已领取订单的详情，可返回 `toUpi`、`cardNumber`、`bankName`、`ifsc` 和 `accountName`。

订单池 `/pay/debit/task` 不包含收款账户。对未领取订单调用 `/pay/order/detail` 已验证会返回 `Task does not exist`。前端领取接口 `/pay/receive/task` 会真实占用订单，因此明确排除。

## 统一模型

新增不可变 `Account`：

- `provider`：渠道名。
- `kind`：`bound_upi`、`bank_account`、`order_payee_upi` 或 `order_payee_bank`。
- `account_id`：渠道内稳定标识；没有服务器 ID 时使用非敏感确定性摘要，避免把完整账号作为对象 ID。
- `account`：可选账户名称/账号。
- `upi`：可选 UPI VPA。
- `bank_name`、`ifsc`：可选银行信息。
- `order_id`：仅订单收款方存在。
- `attributes`：状态、是否启用等安全渠道字段。

`ProviderResult` 增加 `accounts` 元组。失败渠道仍返回空账户；部分渠道可以同时保留已取得的订单和账户。

账户采集失败不应丢失已经完整取得的订单池。ATG Provider 将账户失败记录在 `metadata.account_warnings`，渠道仍可为 `success`；这样可信订单总计不会因为附加账户接口暂时不可用而消失。认证失效仍按现有流程重登一次；持续认证失败按渠道认证错误处理。

## 金额区间

`summarize_orders` 的 `amount_distribution` 改为固定五行：

| key | label | 条件 |
| --- | --- | --- |
| `below_100` | `<100` | `x < 100` |
| `100_10000` | `100-10000` | `100 <= x < 10000` |
| `10000_20000` | `10000-20000` | `10000 <= x < 20000` |
| `20000_50000` | `20000-50000` | `20000 <= x <= 50000` |
| `above_50000` | `>50000` | `x > 50000` |

每行包含 `key`、`label`、`minimum`、`maximum`、`minimum_inclusive`、`maximum_inclusive`、`count`、`percentage` 和 `subtotal`。即使区间为空也保留该行，便于多个渠道稳定对比；当完全没有订单时，五行的数量、百分比和小计均为零。

## ATG 只读采集流程

1. 登录并抓取订单池，保持现有分页完整性判断。
2. 调用收款 UPI 列表和银行卡列表。
3. 分页调用已领取订单列表。
4. 对已领取订单逐个调用详情；只保存存在 `toUpi` 或银行卡字段的收款方。
5. 按 `(kind, account_id, order_id)` 去重并映射为统一 `Account`。
6. 任一附加账户接口失败时记录安全警告，继续生成订单池报告。

为避免请求失控，已领取订单沿用分页 `total` 并设置有限页数检查；详情按顺序只读调用，不并发轰击接口。客户端路径使用显式 allowlist，只允许上述读取端点和既有登录/订单池端点。

## 输出

终端在每个渠道的订单摘要后显示：

```text
  账户: 3
    收款 UPI: a***z@p***m
    银行账户: ****1234 / HDFC / IFSC ****0012
    订单收款方: AP123 / 8***7@y***l
```

终端脱敏保留足够的末尾字符用于人工区分，但不显示完整账号。没有账户时显示 `账户: 0（当前账号未返回已绑定或已领取订单账户）`。

`aggregate.json` 在每个 `channels.<provider>` 下增加：

```json
{
  "account_summary": {
    "count": 3,
    "by_kind": {"bound_upi": 1, "bank_account": 1, "order_payee_upi": 1}
  },
  "accounts": []
}
```

`accounts` 保存完整字段，但不会包含密码、Token、Cookie、Session Key 或签名。账户不写入订单 CSV，避免把敏感标识扩散到更多文件。

## 测试

- 金额恰好为 `100`、`10000`、`20000`、`50000` 时落入唯一正确区间。
- 空订单仍返回固定五个零值区间。
- 账户模型验证类型、渠道一致性和不可变属性。
- ATG 客户端只允许并正确签名四个新增只读端点，认证失效时重登并重新签名。
- UPI、银行卡、已领取订单详情正确映射且去重。
- 附加账户接口失败不会删除成功订单或把敏感原始响应写入警告。
- 终端只出现脱敏账号；JSON 保留完整账号；全部报告不含认证密钥。
- 所有测试使用本地 fake transport，不访问真实支付接口。

## 完成标准

- 每次综合运行同时获取订单池和可安全读取的账户信息。
- 金额分布使用五个固定连续区间，并且订单数、小计分别与总订单数、总金额严格相等。
- 终端不存在完整账户标识，JSON 可供本地后续处理。
- 任何代码路径都不会调用领取订单或其他资金相关写接口。
- 全部自动化测试和编译检查通过。
