# 多渠道订单池聚合架构设计

日期：2026-08-12

## 目标

把当前只支持 ATG Pay 的订单池脚本重构为可扩展的多渠道系统。每次运行并发调用所有已启用渠道，输出一个综合结果，同时保留每个渠道的订单数、金额、金额分布、完整性和错误状态。

本阶段完成多渠道框架并接入 `atgpay`。后续渠道在取得接口、登录和签名规则后，通过新增 Provider 接入，不需要修改聚合核心。

## 已确认的产品行为

- 每次运行调用全部已启用渠道。
- 渠道之间并发执行。
- 一个渠道失败、超时或返回不完整数据时，其他渠道继续运行并正常返回。
- 最终结果同时包含顶层 `total` 和以名称区分的渠道结果，例如 `atgpay`、`xxxpay`。
- 所有渠道统一使用 INR，因此成功渠道的订单金额可以直接汇总。
- `total` 只包含状态为 `success` 且分页完整的渠道。
- `partial` 渠道保留已取得的数据和统计，但不进入可信总计。
- `error` 渠道返回脱敏错误，不返回密码、Token、Cookie、签名或原始认证响应。

## 方案选择

采用显式 Provider 注册表，而不是配置驱动 HTTP 引擎或动态插件系统。

每个渠道由独立 Python Provider 实现统一接口。渠道内部负责自己的配置、登录、签名、分页和响应解析；核心层只处理标准结果。这种方案适合各支付渠道认证和分页规则差异较大的情况，同时避免当前阶段引入外部插件的版本、安全和发布成本。

注册表只加载仓库内显式注册的受信任 Provider，不扫描或执行任意外部代码。

## 架构

### 核心层

核心层不依赖任何 ATG 专属字段。

- `models`：统一订单、渠道结果、综合结果和状态模型。
- `registry`：维护可用 Provider，并根据配置选择全部已启用渠道。
- `runner`：使用有界线程池并发执行 Provider，隔离渠道异常。
- `aggregate`：计算跨渠道总订单数、总金额和金额分布。
- `reporting`：基于同一聚合模型生成终端、JSON 和 CSV 输出。
- `wallet_quota.py`：新的综合命令行入口。

### Provider 层

每个 Provider 是独立、可测试的单元，至少提供：

- 稳定且唯一的渠道名，例如 `atgpay`。
- 从环境配置判断是否启用及读取本渠道配置。
- 执行认证和订单池分页。
- 将原始订单映射为统一订单模型。
- 返回分页完整性、抓取时间和渠道专属元数据。
- 将可预期错误转换为安全的渠道错误分类。

`AtgProvider` 会复用当前已经验证的 ATG 登录、签名、请求重试、会话重登和分页代码，但这些实现移入 `providers/atg/`，不再暴露给聚合层。

## 统一数据模型

### Order

统一订单至少包含：

- `provider`：渠道名。
- `order_id`：渠道内订单编号。
- `amount`：使用有限 `Decimal` 表示的订单金额。
- `currency`：本项目固定为 `INR`。
- `income`：可选收益金额。
- `balance`：可选含收益金额。
- `attributes`：不参与核心统计的渠道专属安全字段。

跨渠道唯一标识由 `(provider, order_id)` 组成。渠道内仍按 `order_id` 去重，不会把不同渠道恰好相同的订单号错误合并。

### ProviderResult

每个渠道返回：

- `provider`
- `status`：`success`、`partial` 或 `error`
- `orders`
- `summary`
- `metadata`：抓取时间、页数、观察到的 API 总数和完整性等
- `error`：仅错误状态存在，包含安全错误分类和脱敏消息

Provider 不应把普通认证或请求失败抛到聚合边界之外。Runner 会对未预期异常做最后隔离，转换为该渠道的内部错误结果。

### AggregateResult

综合结果包含：

- `total`：成功且完整渠道的可信合计。
- `channels`：以 Provider 名为键的全部渠道结果。
- `metadata`：本次运行起止时间、启用渠道数和整体状态。

`total` 包含成功、部分成功和失败渠道数量，以及可信渠道的：

- 订单数
- 订单总金额
- 最低、最高、平均和中位金额
- 精确金额分布
- 可用时的收益合计与覆盖数量

整体状态为：

- `success`：所有启用渠道均成功且完整。
- `partial`：至少一个渠道为 `partial` 或 `error`，但仍成功生成综合报告。

## 配置

配置继续使用本地 `.env`，敏感信息不进入命令行参数或报告。

使用 `ENABLED_PROVIDERS` 明确列出每次运行的渠道，例如：

```dotenv
ENABLED_PROVIDERS=atgpay
ATGPAY_PHONE=...
ATGPAY_PASSWORD=...
ATGPAY_SORT_TYPE=1
ATGPAY_ORDER_TYPE=4
ATGPAY_PAGE_SIZE=10
```

未来渠道使用自己的前缀，例如 `XXXPAY_*`。已启用渠道缺少必要配置时，不阻止其他渠道启动；该渠道产生 `error` 结果。只有 `.env` 无法读取、`ENABLED_PROVIDERS` 为空或其中不存在任何已注册渠道时，才属于程序级配置错误。

为平滑迁移，`AtgProvider` 在本阶段兼容原有 `ATG_*` 配置名；新的 `ATGPAY_*` 值优先。README 和 `.env.example` 使用新名称，引导后续迁移。

## 并发与故障隔离

Runner 对所有已启用 Provider 提交并发任务，线程数不超过启用渠道数和固定安全上限。每个 Provider 拥有独立客户端、Cookie 容器、登录状态和配置，渠道间不共享可变会话。

HTTP 请求继续使用渠道内超时和有限重试。Runner 不强制杀死正在执行的 Python 线程，因此总运行时限由各 Provider 的请求超时、重试次数和分页上限共同约束。后续若某渠道需要更严格的总时限，应在该 Provider 内实现截止时间检查。

结果顺序不依赖线程完成顺序：终端和 JSON 按注册表顺序输出，保证多次运行格式稳定。

## 数据流

1. CLI 读取基础配置和 `ENABLED_PROVIDERS`。
2. 注册表解析全部启用渠道并为每个渠道构建独立 Provider。
3. Runner 并发执行所有 Provider。
4. Provider 登录、分页获取订单并映射为标准订单。
5. Runner 将成功、部分数据或错误统一为 `ProviderResult`。
6. 聚合器只使用 `success` 结果计算 `total`。
7. 报告层写入本次快照目录，再打印终端摘要。

## 输出

### 终端

终端先显示 `total`，再逐个显示渠道：

```text
total:
  渠道: 成功 1 / 部分 0 / 失败 1
  订单数: 299
  总金额: ₹160500

atgpay: success
  订单数: 299
  总金额: ₹160500
  金额分布: ...

xxxpay: error
  错误: Authentication failed
```

### 文件

每次运行生成独立目录，避免多个渠道文件名冲突：

```text
reports/20260812_153000/
├── aggregate.json
├── atgpay_orders.csv
└── xxxpay_orders.csv
```

`aggregate.json` 包含顶层 `total`、全部 `channels`、各渠道摘要、金额分布、订单和安全元数据。每个成功或部分成功且取得订单的渠道生成独立 CSV。错误渠道不生成空 CSV。

文件继续使用同目录临时文件加原子替换；如果目标时间目录已存在，则追加确定性序号，避免覆盖历史快照。

### 兼容入口

保留 `atg_pool_report.py`，但将它改成只启用 `atgpay` 的兼容入口，沿用原有命令行参数。新的推荐入口是：

```bash
python3 wallet_quota.py
```

## 退出码

- `0`：所有启用渠道均成功且完整。
- `3`：至少一个渠道失败或不完整，但综合报告已成功生成。
- `1`：程序级错误，无法生成综合报告或写入输出。
- `2`：基础配置错误，没有可运行的已注册渠道。

单个渠道的认证失败、接口失败或配置缺失属于渠道错误，使用退出码 `3`，而不是阻止综合输出。

## 安全边界

- 凭据只从本地配置读取，且配置对象的密码字段不参与 `repr`。
- 报告、日志和异常不包含密码、Session Key、Login Token、Cookie、签名或原始认证响应。
- Provider 显式限制允许访问的 API 主机与路径。
- 不绕过 Cloudflare、验证码、登录或访问控制。
- 仅实现读取订单池所需接口，不接单、不付款、不提交 UTR、不绑卡、不修改账户。

## 测试策略

测试全部使用本地假响应，不调用真实支付接口。

- Provider 契约测试：所有 Provider 返回合法名称、状态、货币和有限金额。
- ATG 回归测试：登录、签名、每次重试刷新时间戳、会话重登、分页和错误脱敏。
- 注册表测试：启用、未知、重复和缺少配置的渠道处理。
- Runner 测试：真正并发、结果稳定排序、单渠道异常隔离。
- 聚合测试：只汇总完整成功渠道；跨渠道订单号不冲突；金额分布和可选字段覆盖正确。
- 报告测试：终端结构、综合 JSON、渠道 CSV、原子写入和目录冲突处理。
- CLI 端到端测试：全部成功、部分成功、全部渠道失败、基础配置错误和兼容入口。

## 完成标准

- 当前 ATG 功能通过 `atgpay` Provider 工作，既有安全和分页行为不退化。
- 新入口一次运行全部已启用 Provider，并输出 `total` 与每渠道结果。
- 一个 Provider 失败不会阻止其他 Provider 或报告生成。
- 新增渠道只需实现 Provider、添加配置和显式注册，不需要修改聚合器。
- 综合 JSON 和每渠道 CSV 不包含任何会话凭据。
- 全部自动化测试和编译检查通过。
